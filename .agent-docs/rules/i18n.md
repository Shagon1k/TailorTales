# i18n Key Naming

## Principle

A key path must carry enough context to identify the copy **without opening the locale file**.

## Namespace segments (non-leaf)

Name a **semantic concept or content topic** — not a UI position, index, or component type.

```
❌  section1, step2, q3, a3        — positional
✅  dataRetention, cancelFlow, shippingAddress — conceptual
```

**Structural region namespaces** (`hero`, `footer`, `nav`, `form`) are acceptable as top-level containers. Their children must still follow this rule.

**Route/page namespaces** (`home`, `pricing`, `settings`) are always acceptable.

## Leaf keys (terminal)

Standard **role suffixes** are allowed when the parent already provides content context:

| Allowed                                  | Forbidden                                 |
| ---------------------------------------- | ----------------------------------------- |
| `title`, `body`, `heading`, `subheading` | `sub` → use `subheading`                  |
| `label`, `eyebrow`, `tagline`            | `copy` → use `body` or `description`      |
| `cta`, `button`, `link`                  | `q1`, `a1` → pair under a semantic parent |
| `placeholder`, `hint`, `error`           | abbreviations → spell out the role        |
| `question`, `answer`                     |                                           |

## Don't transcribe copy into key names

Name the **topic or role**, not the value. Copy changes; the concept usually doesn't.

```
❌  whereQuestionsBecome   — mirrors the headline, rots when copy changes
✅  hero.heading            — names the role

❌  yourDataIsYours         — paraphrases the value
✅  privacy.hero.heading    — route + region + role is unambiguous
```

Topic names describing _what the section is about_ (not _what it says_) are fine — e.g. `dataRetention`, `refundPolicy`.

## Grouping repeated items

Never number semantically distinct items. Group each under a semantic parent:

```json
// ❌
"q1": "Can I cancel any time?",
"a1": "Yes — at the click of a button…"

// ✅
"cancelAnyTime": {
    "question": "Can I cancel any time?",
    "answer": "Yes — at the click of a button…"
}
```

## Shared option sets

When the same semantic option labels appear in multiple surfaces, define them once in a
shared namespace and reference that namespace everywhere.

```json
// ❌ duplicated in multiple feature trees
"workshop": { "genrePicker": { "fairyTale": { "label": "Fairy tale" } } }
"home": { "tales": { "card": { "genres": { "fairyTale": "Fairy tale" } } } }

// ✅ one shared source, feature trees keep only local hints/help text
"storyOptions": { "genres": { "fairyTale": "Fairy tale" } }
"workshop": { "genrePicker": { "fairyTale": { "hint": "..." } } }
```

Use this for reusable enums and taxonomy-like labels such as genres, writing styles,
formats, languages, statuses, and similar option sets. Duplicate only when the wording
must intentionally diverge by context.

## Quick-reference

```
❌ settings.section1.title  →  ✅ settings.dataRetention.title
❌ checkout.steps.step1     →  ✅ checkout.steps.addItems
❌ home.hero.sub            →  ✅ home.hero.subheading
❌ profile.card.copy        →  ✅ profile.card.body
❌ faq.q1 / faq.a1         →  ✅ faq.cancelAnyTime.question / .answer
```
